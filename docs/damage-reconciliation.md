# 合刀伤害修正与整王校验

## 行为

原有即时修正继续工作：连续快照可确认击杀前血量时，播报与入库直接使用有效伤害。证据不足时照常播报原始伤害，再提交整王校验。后台只更新战报、统计和更新标记，不发送更正群消息。

`recorddao.damage` 保持有效伤害含义，新增：

- `raw_damage`：详细战报的原始伤害，旧记录默认未知，不从有效伤害反推。
- `clan_battle_id`、`server_battle_log_id`：会战归属和服务器战报标识。
- `correction_method`、`correction_evidence`、`corrected_at`：修正方式、JSON 依据和时间。

战报明细 API 增加同名可选字段，前端现有伤害字段和汇总算法不变。角色伤害明细仍使用原始值。

## 何时允许整王补算

后台通过 `clan_battle/boss_info` 获取出刀次数和击破状态，通过 `clan_battle/boss_history` 获取对应王的出刀次数与击破时间，分页读取详细战报；采集前后再次核对状态和次数。协议定义来自本机现有 autopcr 模块，测试使用模拟返回，尚未用真实账号验证服务端实际可用性。

必须同时满足：

1. 两个接口确认该周目该王已击破，出刀次数一致。
2. 唯一详细战报数量等于服务器次数；同玩家同秒的多条记录视为歧义。
3. 存在唯一的击杀记录，或存在唯一的最终战报且结束时间等于服务器击破时间。
4. 最大血量来源明确，前序伤害合计未超过最大血量，尾刀有效伤害大于零且不超过原始值。
5. 入库记录唯一匹配，已知原始伤害与接口一致，已有即时修正没有冲突。

计算为 `尾刀有效伤害 = 最大血量 − 前序原始伤害合计`。前序记录在入库时还会核对有效伤害是否与原始伤害一致，存在矛盾则停止该群的自动修改。

最大血量优先来自保存的服务器快照；缺失时国服可使用本期阶段配置并在依据中记录来源和数值。台服缺少服务器快照时不套用国服配置。血量来源冲突时转为未解决，不能凭“分页拉完”或尾刀时长猜测缺失证据。

## 多群与资源限制

同一进程中只有一个后台 worker，涵盖接入该进程的全部 QQ 机器人账号。群数据按 `group_id` 隔离；采集任务按平台、公会、会战、周目、Boss 去重，同一公会的多个群共享接口采集。

| 项目 | 上限或策略 |
| --- | --- |
| 游戏后台请求 | 全进程并发 1，间隔至少 5 秒 |
| 单游戏账号 | 间隔至少 30 秒，最多 2 次/分钟 |
| 账号繁忙 | 前台请求或等待者优先，后台不排队抢占 |
| 单次后台请求 | 5 秒超时，不在客户端内部自动重发 |
| 普通监控提交 | 仅提交内存事实，不访问校验 SQLite 表或等待接口 |
| 提交缓冲 | 512 个 Boss 事件、512 个群注册项；超额的击杀在监控中有限重试并限频记录告警 |
| 缓存 | 128 页、序列化数据合计 8 MiB、单页 256 KiB、有效期 60 秒 |
| 缓存采集 | 同一公会每 5 秒最多接收一页，保留必要数字字段，不保留角色列表、名字或凭据 |
| 单页 / 单王 | 100 条 / 10,000 条；历史和详细战报各最多扫描 200 页 |
| SQLite | 独立 NullPool，繁忙等待最多 100 毫秒；无网络等待期间持有的事务 |
| 批处理 | 一次回填最多 99 条；重置与过期清理分批处理，每表每批最多 100 条 |
| 空闲状态 | 无新提交时最多每 30 秒检查一次数据库 |
| 自动重试 | 30 秒、2 分钟、10 分钟、30 分钟，±20% 抖动，此后每 30 分钟重试；24 小时后停止 |
| 证据保留 | 30 天，分批清理 |

后台请求开始后无法抢占，普通请求可能等待当前后台请求结束，最多受 5 秒超时约束。所有群共享额度意味着繁忙时补算会排队，不代表生产环境零开销。多进程或多机器共用账号不在本次协调范围内。
